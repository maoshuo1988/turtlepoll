# 撕裂带特性详情介绍

## 1. 状态机

### 1.1 热度计算主状态机

状态定义:

- `INIT`: 上游业务实体已创建，但未进入热度计分窗口。
- `COLLECTING`: 热度计分窗口打开，接收下注/评论/回复/点赞输入。
- `FROZEN`: 热度计分窗口关闭，不再接收计分输入，仅读快照。
- `SETTLED`: 热度快照已被下游消费并完成结算归档。

状态流转:

- `INIT -> COLLECTING`: 上游模块发出“开放计分窗口”信号。
- `COLLECTING -> FROZEN`: 上游模块发出“关闭计分窗口”信号。
- `FROZEN -> SETTLED`: 下游完成热度结果消费并确认结算批次。
- `SETTLED` 为终态；同一 `bizId + roundId` 不可重复回退到 `COLLECTING`。

### 1.2 热度计算状态机与对立PK映射

说明：本映射为单向读取，即本域根据对立PK状态变化推断热度计算状态的含义，但本域状态变化不会反向驱动或影响对立PK的状态机。本域的任何计算结果或错误都不会阻塞对立PK的业务流程。

映射规则:

| 对立PK状态 | 热度计算状态 | 说明 |
|------|------|------|
| `betting` | `COLLECTING` | 接收下注与互动计分输入 |
| `locked` | `COLLECTING` | 禁止下注但继续接收互动计分输入 |
| `settle_ready=true 且 now >= endTime` | `FROZEN` | 冻结快照，不再接收计分输入 |
| `settled` | `SETTLED` | 热度结果已消费并完成结算归档 |

触发约束:

- 对立PK达到 `endTime` 后，首次结算请求或轮询保底任务都必须先触发 `ComputeHeatSnapshot`，将热度状态从 `COLLECTING` 幂等推进到 `FROZEN`。
- 若同一回合已存在 `FROZEN` 快照，再次触发 `ComputeHeatSnapshot` 必须返回同一份冻结结果，不得生成新的 `SETTLE` 快照。
- 对立PK同一回合仅允许一次 `FROZEN -> SETTLED` 消费确认。
- 为兼容旧调用方，未显式声明 `snapshotType` 的 ComputeHeatSnapshot 仍按 CHECKPOINT 语义执行，不触发状态推进。

### 1.3 热度计算状态机与暗盘映射

说明：本映射为单向读取，即本域根据暗盘状态变化推断热度计算状态的含义，但本域状态变化不会反向驱动或影响暗盘的状态机。本域的任何计算结果或错误都不会阻塞暗盘的业务流程。

映射规则:

| 暗盘状态 | 热度计算状态 | 说明 |
|------|------|------|
| `NOT_OPEN` | `INIT` | 未开放，仅保留实体占位 |
| `OPEN` | `COLLECTING` | 接收下注与互动计分输入 |
| `CLOSED` | `COLLECTING` | 禁止下注但允许互动计分输入 |
| `SETTLED` | `FROZEN` | 冻结快照，等待下游消费 |
| `TEAR_SETTLED` | `SETTLED` | 热度结果已被消费并完成归档 |

触发约束:

- 暗盘从 `OPEN/CLOSED` 进入 `SETTLED` 时必须先冻结热度快照。
- 暗盘的 `TEAR_SETTLED` 仅在热度结算消费成功后写入，不依赖预测市场状态机实现细节。

## 2. 下注对象

### 2.1 首次行为锁定下注对象

锁定来源:

- 首次下注: 强锁定。
- 首次顶层预测市场评论或点赞: 弱锁定。

锁定后行为:

- 顶层评论仅允许本下注对象。
- 点赞仅允许本下注对象内容。
- 可跨对象回复，但回复归属本人下注对象。
- 下注对象支持二元 `A/B` 或三元 `A/B/C`（`C` 对应 `DRAW`）。

### 2.2 下注强锁定与换边拦截

规则:

- 用户首次下注后，不允许向其他下注对象下注。
- 用户不可撤销或改边。
- 允许在同下注对象追加下注。

错误语义:

- `TEAR_CAMP_LOCKED_BY_BET`: 已被下注锁定。
- `TEAR_CAMP_CONFLICT`: 已在对方阵营弱锁定，禁止跨阵营下注。

兼容约束:

- 历史错误码 `CAMP_LOCKED_BY_BET` 统一映射到 `TEAR_CAMP_LOCKED_BY_BET`。
- 历史错误码 `CAMP_CONFLICT` 统一映射到 `TEAR_CAMP_CONFLICT`。

### 2.3 跨对象回复归属规则

定义:

- 回复位置可跨对象。
- 热度归属按回复者下注对象，不按被回复楼层对象。

结果:

- 跨对象对线可提升对方线程活跃，但热度记到自己下注对象。

### 2.4 阵营归属边界与冲突决策表

统一字段:

- `current_option`: 用户当前阵营（由强锁定优先，其次弱锁定）。
- `option_at_action`: 本次互动发生时写入阵营，落库后不可回溯修改。

决策优先级:

1. 强锁定（BET）
2. 弱锁定（INTERACT）
3. 无锁定

冲突决策表:

| 场景 | 输入 | 判定 | 返回码 | 落库规则 |
|------|------|------|------|------|
| 首次下注 | 用户无锁定，下注 option=X | 建立强锁定 X | 无 | `current_option=X` |
| 强锁定后同阵营追加下注 | 强锁定 X，下注 option=X | 允许 | 无 | 保持 `current_option=X` |
| 强锁定后跨阵营下注 | 强锁定 X，下注 option=Y 且 Y!=X | 拒绝 | `TEAR_CAMP_LOCKED_BY_BET` | 不写入 |
| 弱锁定后同阵营下注 | 弱锁定 X，下注 option=X | 允许并升级强锁定 | 无 | 锁定类型升级为 BET |
| 弱锁定后跨阵营下注 | 弱锁定 X，下注 option=Y 且 Y!=X | 拒绝 | `TEAR_CAMP_CONFLICT` | 不写入 |
| 顶层评论 | `current_option=X`，评论 tab=X | 允许 | 无 | `option_at_action=X` |
| 顶层评论跨阵营 | `current_option=X`，评论 tab=Y 且 Y!=X | 拒绝 | `TEAR_CAMP_CONFLICT` | 不写入 |
| 跨对象回复 | `current_option=X`，被回复内容属于 Y 且 Y!=X | 允许 | 无 | `option_at_action=X` |
| 点赞同阵营 | `current_option=X`，被点赞作者阵营 X | 允许 | 无 | 记点赞输入到 X |
| 点赞跨阵营 | `current_option=X`，被点赞作者阵营 Y 且 Y!=X | 拒绝 | `TEAR_CAMP_CONFLICT` | 不写入 |

一致性约束:

- 查询场景必须以 `option_at_action` 作为历史归属来源，不允许用 `current_option` 覆盖历史。
- 若历史数据缺失 `option_at_action`，按“写时 current_option”回填一次后固化，后续禁止再次改写。

## 3. 热度

### 3.1 点赞热度累计

公式:

$$
H_{like}=\sum 1
$$

约束:

- 每用户对同一目标最多点赞 1 次。
- 不支持取消点赞回滚热度。

### 3.2 评论热度简化计算（A/U/T/C固定为1）

固定参数:

- $A_i=1$
- $U_i=1$
- $T_i=1$
- $C_i=1$
- $Q_i=1$ (MVP)

公式:

$$
Base_i=3
$$

$$
Comment_i=min(3\times(1+log(1+L_i)),20)
$$

$$
H_{comment}=\sum Comment_i
$$

### 3.3 投币热度线性缩放（amount×0.02）

公式:

$$
H_{coin}=\sum (BetAmount_i\times0.02)
$$

口径:

- `BetAmount_i` 为用户在本下注对象累计下注额。
- 同用户多次下注按累计额线性计入热度。

## 4. 结算

### 4.1 暗盘实时结算池

规则:

- 资金来源: 用户下注总额 100%。
- 分配依据: 按每笔下注锁定赔率 `bet.odds` 结算。
- 失败方下注不返还。

### 4.2 暗盘撕裂带池10%铸币

公式:

$$
Pool_{tear}=max((\sum V_{option,user})\times10\%,10)
$$

规则:

- 基于实际用户下注额，不含虚拟底池；二元与三元市场统一适用。
- 最低铸币 10。

### 4.3 撕裂带池按胜方评论热度分配

资格:

- 仅 PK 胜方下注对象下的评论/回复作者参与。
- 官方账号不参与。

公式:

$$
Reward_i=Pool_{tear}\times\frac{H_{comment,i}}{\sum H_{comment,win}}
$$

## 5. 幂等与审计

### 5.1 结算任务按eventId幂等

幂等键:

- `eventId + settleType + settleVersion`

要求:

- 同一键重复执行不重复入账。
- 任务失败可重试，最多 3 次。

### 5.2 奖励发放审计与复算

审计字段:

- `eventId`
- `camp`
- `userId`
- `heatSnapshot`
- `rewardAmount`
- `txId`
- `settleBatchId`

复算能力:

- 使用审计快照可离线复算总分配额。
- 复算误差容忍 `<= 1`（最小货币单位）。

## 6. 增强项

### 6.1 未开放订阅通知

规则:

- 支持未开放事件订阅。
- 事件转已开放时单次推送。

### 6.2 高频互动权重衰减提示

规则:

- 用户第 3 条评论开始展示衰减提示。
- 第 6 条及以上增加二次提示。

### 6.3 守擂与翻盘标识

规则:

- 上局胜方本局继续领先: 守擂。
- 上局胜方本局落后: 翻盘。

## 7. 远期项

### 7.1 争议结算人工仲裁窗口

设计中项:

- 结果确认后 24h 内允许运营发起仲裁。

### 7.2 历史局全景回放

设计中项:

- 提供按事件维度回放热度变化时间线。

## 8. 查询与展示能力

### 8.1 事件热度榜单查询

目标:

- 支持查询事件全量热度榜单。
- 支持按“我当前下注对象”过滤榜单（本方榜单）。
- 对应接口：GET /api/pk/heat/rank。

返回字段:

- `userId`
- `username`
- `avatar`
- `option`
- `totalHeat`

排序规则:

- 按 `totalHeat` 倒序。
- `totalHeat` 相同按 `first_action_time` 升序。

过滤规则:

- `scope=ALL` 返回全榜。
- `scope=MY_SIDE` 仅返回与当前用户 `myOption` 相同的榜单。

### 8.2 我的事件数据查询

目标:

- 提供当前用户在指定事件下的聚合数据视图。

返回字段:

- `myOption`：我当前下注对象（`A/B/C`）。
- `receivedLikeCount`：我在该事件评论/回复收到的点赞总数。
- `myCommentCount`：我在该事件的评论与回复条数。
- `myBetAmount`：我在该事件累计下注额。
- `estimatedPayout`：按当前热度与奖池估算可得派奖。
- `myTotalHeat`：我在该事件累计热度。

计算规则:

- `myTotalHeat = myLikeHeat + myCommentHeat + myCoinHeat`。
- `estimatedPayout` 在未冻结时为实时估算值；冻结后为冻结估算值。

### 8.3 当前下注赔率查询

目标:

- 支持在下注前查询各 option 当前赔率。

返回字段:

- `option`
- `poolAmount`
- `odds`
- `snapshotTime`

规则:

- 二元场景返回 `A/B`；三元场景返回 `A/B/C`。
- 赔率按当前奖池实时计算，不改写已下注订单锁定赔率。

### 8.4 评论回复归属option记录

规则:

- 评论与回复写入时必须记录作者当时的 `option`，字段名 `option_at_action`。
- 该字段一经写入不可回溯修改，用于审计与榜单归属计算。
- 当用户后续发生阵营变化（若业务允许）时，历史评论与回复仍保持原 `option_at_action`。

### 8.5 评论回复查询返回option

规则:

- 评论与回复列表查询必须返回 `option` 字段。
- 返回的 `option` 取 `option_at_action`，不使用实时阵营覆盖。
- 回包中应包含 `commentId/userId/option/content/createTime` 基础字段。
