# 撕裂带总览与边界

## 1. 设计原则

本设计遵循以下原则，确保热度计算领域不对暗盘与对立PK造成反向依赖或影响：

### 1.1 支撑性领域

- 热度计算是纯支撑性服务域，为暗盘与对立PK提供计算能力，不反向依赖或约束上游业务。
- 热度计算不定义上游系统应该如何组织业务流程、何时触发计分窗口、何时关闭计分。
- 热度计算不关心上游系统的具体玩法设计，只关心规定的输入与输出口径。

### 1.2 被动接收模式

- 热度计算采用完全被动的接收模式：上游系统发出信号（开放计分、关闭计分、消费结果），本域响应并执行对应的状态流转与计算。
- 热度计算不主动向上游发起任何业务操作或流程推进请求。
- 上游系统可独立修改业务流程、玩法规则、触发时机，只需保证输入与输出接口相同。

### 1.3 技术无关性

- 热度计算不耦合暗盘或对立PK的具体实现细节（如两者的状态机设计、存储结构、依赖系统）。
- 映射关系仅用于本域理解上游信号的含义，不假设上游系统如何实现这些状态。
- 两个业务域可独立演进技术栈，只需遵守接口契约。

### 1.4 可扩展性

- 热度计算架构支持任意第三方业务域的接入，只需遵守 `bizType` + 输入参数 + 输出快照的标准。
- 无需修改热度计算系统核心逻辑，即可支持新的业务场景。

## 2. 目标

- 为暗盘与对立PK提供统一的热度计算能力，形成可量化热度对抗。
- 只定义热度口径、归属与快照输出，不定义上层玩法的触发流程。
- 为对立PK的胜负判定和暗盘的讨论收益分配提供一致的热度输入。

## 3. 业务对象

- 事件: 预测市场事件（暗盘）。
- 回合: 对立PK的单局对抗实体。
- 下注对象: 取自预测市场下注对象，支持二元 `A/B` 或三元 `A/B/C`（`C` 对应平局 `DRAW`）。
- 用户行为: 围绕暗盘或对立PK的下注、评论、回复、点赞、投币。
- 热度: 点赞热度 + 评论热度 + 投币热度。

## 4. 状态机边界

热度计算状态机独立定义，不复用暗盘或对立PK的业务状态机实现:

- 主状态机: `INIT -> COLLECTING -> FROZEN -> SETTLED`
- 映射原则: 上游业务状态变更通过映射驱动热度状态流转

对立PK映射:

- `betting/locked -> COLLECTING`
- `settle_ready && now >= endTime -> FROZEN`
- `settled -> SETTLED`

暗盘映射:

- `NOT_OPEN -> INIT`
- `OPEN/CLOSED -> COLLECTING`
- `SETTLED -> FROZEN`
- `TEAR_SETTLED -> SETTLED`

## 5. 能力边界

本设计包含:

- 站队锁定规则
- 热度口径与计算
- 热度快照与下游消费契约
- 接口契约与错误码
- 配置项与初始化数据

本设计不包含:

- 上层玩法的发起、路由与状态推进
- 话题及话题种子的创建与管理（由对立PK领域负责）
- 前端视觉规范细节（仅保留字段与状态要求）
- 推荐系统分发算法
- 反作弊模型训练细节

## 6. 一致性规则

- 下注后下注对象永久锁定，不可撤销。
- 顶层预测市场评论只能发在本人下注对象下，回复允许跨对象。
- 点赞只能给同下注对象内容。
- 热度结算窗口关闭后，互动不再影响热度。
- 对立PK在 `now >= endTime` 后可由用户结算接口或轮询保底任务触发一次惰性冻结。

## 7. 成功标准

- 暗盘: 可输出可审计的热度快照，供下游结算消费。
- 对立PK: 可输出可审计的热度快照，供胜负判定消费。
- 统一口径: 同一事件或回合内热度计算结果可复算。
