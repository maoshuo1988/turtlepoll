# 体力模型、站内预测数据与推送设计

> 本文补充三块落地方案：AI 体力模型、站内预测数据上下文、主动推送链路。当前代码里主动聊天先用龟币扣费承接，本文给出后续独立体力模型的目标方案。

## 1. AI 体力模型

### 1.1 目标

体力用于控制用户主动调用 LLM 的频率和成本，和龟币账户分开：

- 用户主动聊天消耗体力。
- 主动推送不消耗体力。
- DeepSeek 失败不消耗体力。
- 体力不足时不调用 DeepSeek，返回固定兜底文案。
- 用户可以通过自然恢复、苹果、运营赠送等方式恢复体力。

### 1.2 数据模型

建议新增用户 AI 体力状态表：

```text
user_ai_stamina
  user_id              PK
  stamina              当前体力
  max_stamina          体力上限，默认 5
  last_recover_at      上次自然恢复结算时间
  daily_used_date      当日使用计数日期，YYYYMMDD
  daily_used_count     当日主动聊天消耗次数
  create_time
  update_time
```

建议新增体力流水表：

```text
user_ai_stamina_log
  id
  user_id
  biz_type             CHAT / RECOVER / APPLE / ADMIN / REFUND
  biz_id               关联消息、订单或操作 ID
  amount               正数恢复，负数消耗
  stamina_after
  remark
  create_time
```

### 1.3 体力规则

| 项 | 建议值 | 说明 |
| --- | --- | --- |
| 初始体力 | 5 | 新用户首次创建状态时给满。 |
| 体力上限 | 5 | 后续可由会员、宠物能力或活动提高。 |
| 主动聊天消耗 | 1 | 每次 DeepSeek 成功后扣除。 |
| 自然恢复 | 每 60 分钟 +1 | 到达上限后不再恢复。 |
| 苹果恢复 | 5 龟币恢复 1 点 | 对应兜底文案“喂它一颗苹果”。 |
| 每日主动消息上限 | 50 | 成本保护，独立于体力。 |

### 1.4 扣减流程

```text
用户发送消息
  -> GetOrCreateStamina(userId)
  -> RecoverByTime(now)
  -> 校验 stamina >= cost
  -> 校验 daily_used_count 未超限
  -> 调用 DeepSeek
  -> DeepSeek 成功后事务内：
       1. 保存用户消息
       2. 保存助手消息
       3. 扣体力
       4. 写体力流水
  -> DeepSeek 失败：
       不保存成功对话，不扣体力，返回降级文案
```

关键点：

- 体力扣减必须在 DeepSeek 成功之后。
- 保存消息、扣体力、写流水应在同一事务内。
- 自然恢复可以在每次读体力时懒结算，不必单独定时任务。
- 并发请求需要对 `user_ai_stamina` 行加锁，避免体力被同时扣成负数。

### 1.5 接口建议

```text
GET /api/ai/stamina
```

返回：

```json
{
  "stamina": 3,
  "maxStamina": 5,
  "nextRecoverAt": 1760000000,
  "dailyUsedCount": 2,
  "dailyLimit": 50
}
```

```text
POST /api/ai/stamina/apple
```

请求：

```json
{
  "count": 1
}
```

处理：

- 扣除 `count * 5` 龟币。
- 恢复 `count` 点体力，但不能超过 `max_stamina`。
- 写金币流水和体力流水。

### 1.6 与当前实现的关系

当前已实现：

- `aiChat.defaultStaminaCost` 配置。
- 聊天前校验用户龟币余额。
- DeepSeek 成功后按 `AI_CHAT` 扣龟币。
- DeepSeek 失败不扣龟币。

后续迁移：

1. 新增 `user_ai_stamina` 和 `user_ai_stamina_log`。
2. `AIChatService` 从“扣龟币”改为“扣体力”。
3. 保留苹果购买接口：龟币只在恢复体力时消耗。
4. `ai_message.stamina_cost` 继续记录本次消耗体力点数。

## 2. 站内预测数据上下文

### 2.1 目标

当用户在预测市场详情页或比赛页问小龟时，后端应该读取站内事实，再把结构化上下文交给 LLM：

- 只使用站内可信数据，不让模型编造市场状态。
- 回复可以给倾向，但必须带风险提醒。
- 不读取外部实时数据，除非后续明确接入外部数据源。

### 2.2 支持的上下文类型

| contextType | contextId | 数据来源 | 用途 |
| --- | --- | --- | --- |
| `predict_market` | `PredictMarket.Id` | `PredictMarket` + `PredictContext` + 聚合下注数据 | 预测市场分析。 |
| `match_schedule` | `MatchSchedule.Id` | `MatchSchedule` + 关联市场 | 比赛基础分析。 |
| `pk_topic` | `PKTopic.Id` | `PKTopic` + 当前 `PKRound` | 对立 PK 话题分析。 |
| `battle` | `Battle.Id` | 开战广场赌局 | 赌局规则和参与风险说明。 |

MVP 建议先实现 `predict_market`。

### 2.3 预测市场上下文字段

建议由 `PredictContextService` 或新增 `AIMarketContextService` 生成：

```json
{
  "marketId": 123,
  "title": "2026 世界杯决赛谁会夺冠？",
  "status": "OPEN",
  "closeTime": 1760000000,
  "eventName": "世界杯决赛",
  "detail": "站内运营填写的事件说明",
  "tags": ["football", "world-cup"],
  "options": [
    {
      "key": "A",
      "label": "法国",
      "pool": 1200,
      "odds": 1.8,
      "voteCount": 32
    },
    {
      "key": "B",
      "label": "巴西",
      "pool": 900,
      "odds": 2.1,
      "voteCount": 21
    }
  ],
  "participantCount": 53,
  "resolved": false,
  "myBet": {
    "option": "A",
    "amount": 100,
    "odds": 1.8,
    "status": "OPEN"
  }
}
```

### 2.4 Prompt 拼装

系统消息使用基础人格 Prompt，用户消息前追加站内事实：

```text
下面是站内预测市场上下文，必须只依据这些事实分析：
{{market_context_json}}

用户问题：
{{user_input}}
```

约束：

1. 如果市场已关闭或已结算，必须说明当前不能继续下注。
2. 如果上下文缺少关键数据，必须说明“站内数据还不够完整”。
3. 不允许使用“稳赚”“必胜”“无脑买”等表达。
4. 不输出内部表名、字段名、SQL 或系统实现。
5. 不主动建议大额下注，只能提醒控制仓位。

### 2.5 服务职责

```text
AIChatService
  -> AIRiskService 校验输入
  -> AIContextService 根据 contextType/contextId 取上下文
  -> DeepSeekClient 生成回复
```

| 服务 | 职责 |
| --- | --- |
| `AIContextService` | 统一识别 contextType，分发到具体上下文构建器。 |
| `AIPredictContextBuilder` | 读取预测市场、展示上下文、下注聚合、当前用户下注。 |
| `AIPromptBuilder` | 拼接人格 Prompt、上下文 Prompt、历史消息。 |

### 2.6 权限与安全

- 只返回当前登录用户有权看到的数据。
- `myBet` 只能读取当前用户自己的下注。
- 不把其他用户明细、手机号、邮箱、IP 等敏感信息传给 LLM。
- Prompt 中传 JSON 时做长度限制，避免上下文过大。
- LLM 响应仍需经过敏感词或风险词后处理。

## 3. 主动推送设计

### 3.1 推送类型

| 类型 | scene | 触发 | 是否调用 LLM | 是否消耗体力 |
| --- | --- | --- | --- | --- |
| 结算赢 | `win` | 预测/投票结算后用户盈利 | 否 | 否 |
| 结算输 | `lose` | 预测/投票结算后用户亏损 | 否 | 否 |
| 连胜 | `win_streak` | 连胜达到 3 场及以上 | 否 | 否 |
| 连败 | `lose_streak` | 连败达到 5 场及以上 | 否 | 否 |
| 闲置最大盈利 | `idle_biggest_win` | 用户闲置且有最大盈利记忆 | 否 | 否 |
| 闲置首次开蛋 | `idle_first_egg` | 用户闲置且有首次开蛋记忆 | 否 | 否 |
| 闲置最长连胜 | `idle_longest_streak` | 用户闲置且有最长连胜记忆 | 否 | 否 |

### 3.2 投递通道

优先级建议：

1. SSE：在线用户即时收到，适合服务端到前端的单向推送。
2. 轮询接口：`GET /api/ai/pushes/unread` 兜底。
3. 站内消息：如果需要跨端未读数，可复用现有通知体系。
4. WebSocket：本期不优先使用，除非后续需要双向实时互动。

MVP 推荐：

- 先用 `ai_message` 作为推送存储。
- 前端聊天入口或小龟浮窗轮询未读推送。
- 在线即时体验使用 `GET /api/ai/pushes/stream` SSE。
- 详细协议见 [11-前端推送协议设计.md](./11-前端推送协议设计.md)。

### 3.3 推送生成流程

```text
业务事件触发
  -> AIPushService.ReceiveEvent(event)
  -> 更新 user_ai_memory 中的 streak / 关键事实
  -> 判断是否命中推送场景
  -> AITemplateService.Select(scene, userId)
  -> RenderTemplate(placeholders)
  -> 保存 ai_message:
       role=assistant
       scene=win / lose / win_streak ...
       template_id=xxx
       status=unread
       stamina_cost=0
  -> 写 template_user_view 曝光
  -> 投递 SSE 或等待轮询拉取
```

### 3.4 模板选择

输入：

- `scene`
- `userId`
- `placeholders`

规则：

1. 查询 `dialogue_template where scene=? and enabled=true`。
2. 左连接当前用户 `template_user_view`。
3. 优先选择没有曝光记录的模板。
4. 都曝光过时选择 `view_count` 最少的模板。
5. 同曝光次数下按 `weight` 加权随机。
6. 渲染后检查占位符是否全部替换，未替换则丢弃或降级到固定文案。

### 3.5 结算推送策略

一次结算可能同时命中普通输赢和 streak，MVP 每次最多推一条：

| 条件 | 推送 scene |
| --- | --- |
| `vote_lose_streak >= 5` | `lose_streak` |
| `vote_win_streak >= 3` | `win_streak` |
| 本次盈利 `> 0` | `win` |
| 本次亏损 `< 0` | `lose` |
| 平局、退款、作废 | 不推送 |

优先级：`lose_streak` > `win_streak` > `lose` > `win`。

### 3.6 闲置推送策略

依赖 `user_ai_presence`：

- `active=true`。
- `now - last_seen_at <= 60 秒`，认为用户仍在线。
- `now - last_ai_interact_at >= aiChat.idleTriggerMinutes`。
- `now - last_idle_push_at >= aiChat.idlePushCooldownMinutes`。
- `idle_push_count_date` 是今天且 `idle_push_count < aiChat.idlePushDailyLimit`。

触发顺序：

1. 用户上报 presence。
2. 定时任务每 1 分钟扫描候选用户。
3. 从用户记忆中选择一个可用 idle 场景。
4. 生成 `ai_message` 未读推送。
5. 更新 `last_idle_push_at` 和每日计数。

闲置推送不应该连续重复同一类记忆，可在 `flag_meta.lastPushedAt` 或单独表中记录最近推送场景。

## 4. 推荐落地顺序

1. 先落 AI 体力表、状态查询、聊天扣体力和苹果恢复。
2. 再接 `AIContextService`，让主动聊天能读取预测市场上下文。
3. 然后实现模板选择、渲染、曝光记录和结算推送。
4. 最后补 presence、未读/已读接口、闲置推送和 SSE 即时投递。
