# AI 结算推送链路

> 本文说明投票/预测结算后如何生成和投递推送文案，包括资金入账、事件处理、记忆维护、模板渲染、消息投递等完整流程。

## 1. 完整处理流程

```text
结算服务完成资金入账（PredictSettleService）
  -> 提交资金入账事务成功
  -> 触发 AISettlementEvent
  -> 调用 AIPushService.OnSettlement(event)
  -> 开启新事务
  -> 幂等检查：query ai_message where user_id=? and request_id=settle:{bizType}:{bizId}:{scene}
     ├─ 已存在 -> 跳过此推送，返回成功
     └─ 不存在 -> 继续
  -> AIMemoryService.UpdateSettlementMemory(event)
     - 更新 vote_win_streak / vote_lose_streak
     - 更新 biggest_win_amount / biggest_win_event
     - 更新 longest_win_streak
  -> DecideSettlementScene(event, memory)
  -> AITemplateService.SelectAndRender(scene, userId, placeholders)
  -> 保存 ai_message(role=assistant, status=0, stamina_cost=0, request_id, template_id)
  -> 更新 template_user_view 记录曝光
  -> 提交事务
  -> AIPushDelivery.Deliver(userId, message)
```

## 2. 事件输入规范

### 2.1 事件字段

结算服务调用时组装的 `AISettlementEvent`：

```text
event_id        唯一事件 ID，e.g. predict:settle:{betId} (可选，AIPushService 内生成)
user_id         结算用户 ID
biz_type        predict / vote / pk / battle 等
biz_id          下注单 ID 或结算项 ID
context_type    predict_market / vote / pet / none
context_id      市场 ID 或业务对象 ID
profit_amount   净盈利金额，正数为盈利，负数为亏损，0 不推
settle_result   win / lose / refund / canceled
settled_at      结算时间戳
```

### 2.2 调用示例

```go
event := AISettlementEvent{
  UserId:      user.ID,
  BizType:     "predict",
  BizId:        bet.ID,
  ContextType: "predict_market",
  ContextId:    market.ID,
  ProfitAmount: settlement.Amount, // 结算金额（已入账）
  SettleResult: "win",
  SettledAt:    time.Now().Unix(),
}

// 在资金入账事务提交后调用
aiPushService.OnSettlement(event)
```

## 3. 记忆更新

### 3.1 更新规则

结算时更新 `user_ai_memory` 表：

| 字段 | 更新条件 | 更新逻辑 |
| --- | --- | --- |
| `vote_win_streak` | 盈利结算 | +1，亏损时清零为 0 |
| `vote_lose_streak` | 亏损结算 | +1，盈利时清零为 0 |
| `biggest_win_amount` | 盈利 > 历史最大值 | 更新为新最大值 |
| `biggest_win_event` | 同上 | 记录该事件 ID 或市场信息 |
| `longest_win_streak` | `vote_win_streak` 刷新历史最大值 | 更新为新最大值 |
| `longest_lose_streak` | `vote_lose_streak` 刷新历史最大值 | 更新为新最大值 |

### 3.2 平局与作废

| 结算类型 | 处理 |
| --- | --- |
| `refund` | 不更新 streak，不推送 |
| `canceled` | 不更新 streak，不推送 |
| 平局 | 不更新 streak，不推送 |

## 4. 推送场景决策

### 4.1 决策矩阵

一次结算最多生成一条推送。按优先级从高到低：

| 优先级 | 条件 | scene | 说明 |
| --- | --- | --- | --- |
| 1 | `vote_lose_streak >= 5` | `lose_streak` | 连败 5 场以上 |
| 2 | `vote_win_streak >= 3` | `win_streak` | 连胜 3 场以上 |
| 3 | `profit_amount < 0` | `lose` | 普通亏损 |
| 4 | `profit_amount > 0` | `win` | 普通盈利 |
| - | 其他 | 不推送 | 平局、退款、作废等 |

### 4.2 决策关键点

- **Streak 优先**：连胜/连败优先于普通输赢，提升用户心理反馈。
- **收益口径**：必须使用实际结算净收益，不能用下注本金代替。
- **单结最多一条**：即使用户一天结算 100 单，每单最多一条推送，但可后续加每日上限。

## 5. 幂等性保护

### 5.1 幂等键

```text
request_id = settle:{bizType}:{bizId}:{scene}
```

例：`settle:predict:12345:win_streak`

### 5.2 幂等检查

在消息落库前，先查询是否已存在：

```sql
SELECT id FROM ai_message
WHERE user_id = ? AND request_id = ?
LIMIT 1
```

- 存在：跳过推送，直接返回成功。
- 不存在：继续落库。

### 5.3 并发保护

**关键要求**：

- 幂等检查和 `ai_message` 插入必须在同一事务内。
- 创建唯一索引：`UNIQUE INDEX uniq_ai_message_user_request ON ai_message(user_id, request_id)`。
- 若并发插入触发唯一冲突，数据库自动保证只有一条成功；应用层也能安全处理。

**处理流程**：

1. 开始事务。
2. 幂等检查。
3. 若不存在，INSERT INTO ai_message。
4. 若唯一冲突，捕获错误，视为幂等成功。
5. 提交事务。
6. 事务提交后再做 SSE 投递（不在事务内）。

## 6. 模板选择与渲染

### 6.1 选择算法

```sql
SELECT t.* FROM dialogue_template t
LEFT JOIN template_user_view v ON t.id = v.template_id AND v.user_id = ?
WHERE t.scene = ? AND t.enabled = 1
ORDER BY ISNULL(v.view_count) DESC, v.view_count ASC, RAND() * t.weight
LIMIT 1
```

优先级：

1. **未看过的模板**（`view_count` 为 NULL）。
2. **看得最少的模板**（`view_count` 最小）。
3. **按权重随机**（权重越大，被选中概率越高）。

### 6.2 占位符渲染

声明每个 scene 的占位符集合：

| scene | 占位符 | 类型 | 说明 |
| --- | --- | --- | --- |
| `win` | `{amount}` | 金额 | 盈利金额 |
| `lose` | `{amount}` | 金额 | 亏损金额（绝对值） |
| `win_streak` | `{n}` | 数字 | 连胜场数 |
| `lose_streak` | `{n}` | 数字 | 连败场数 |

### 6.3 渲染与校验

```text
template.content = "连胜 {n} 场了，我看好你!"
placeholders = {n: 3}
result = template.content.replace("{n}", "3")
       = "连胜 3 场了，我看好你!"

// 校验：检查是否还有未替换的占位符
if result.contains("{") {
  // 跳过该模板，尝试下一条
  // 全部失败时使用固定兜底
}
```

### 6.4 兜底模板

若所有模板均无法渲染（缺少占位符、数据库连接失败等），使用固定兜底：

```text
scene win: "不错哦，又赚到了!"
scene lose: "没关系，下次就赢了~"
scene win_streak: "连胜中，继续加油!"
scene lose_streak: "冷静一下，马上反转!"
```

## 7. 消息落库

### 7.1 ai_message 记录

主动推送保存为一条助手消息：

```text
user_id           用户 ID
role              assistant
scene             win / lose / win_streak / lose_streak
content           渲染后的最终文案
template_id       使用的模板 ID
status            0（未读）
stamina_cost      0（推送不消耗体力）
context_type      predict_market / vote / pet / none
context_id        业务对象 ID
request_id        幂等键 settle:{bizType}:{bizId}:{scene}
model             无（推送不调用 LLM）
create_time       now()
```

### 7.2 data 约束

- `status` 初始值必须为 `0`（未读）。
- `stamina_cost` 必须为 `0`。
- `request_id` 必须非空。
- 建议加唯一索引：`UNIQUE INDEX uniq_ai_message_user_request(user_id, request_id)`。

## 8. 曝光记录

### 8.1 template_user_view

每次推送成功后，记录模板曝光：

```text
user_id
template_id
view_count          初次为 1，后续 +1
last_viewed_at      now()
```

### 8.2 Upsert 操作

```sql
INSERT INTO template_user_view (user_id, template_id, view_count, last_viewed_at)
VALUES (?, ?, 1, now())
ON DUPLICATE KEY UPDATE
  view_count = view_count + 1,
  last_viewed_at = now()
```

建议唯一索引：`UNIQUE INDEX uniq_template_user_view(user_id, template_id)`。

## 9. 投递编排

### 9.1 投递时机

消息落库后（事务提交后），立即调用投递接口：

```go
// 事务内
saveMessage(message)
updateTemplateView(userId, templateId)
// 事务外（committed 后）
pushDelivery.Deliver(userId, message)
```

### 9.2 投递方案

`AIPushDelivery` 接口：

```go
type AIPushDelivery interface {
  Deliver(userId int64, message AIMessage) error
}
```

MVP 实现：

- `no-op`：消息落库即完成，不做实时投递。
- 前端通过 `GET /api/ai/pushes/unread` 定期轮询。

即时体验实现：

- 如消息 `status=0`（未读）且在线用户，通过 SSE 投递。
- 见 [04-特性详情介绍-闲置推送链路.md#4-投递与已读](./04-特性详情介绍-闲置推送链路.md#4-投递与已读)。

### 9.3 失败兜底

- 投递失败（SSE 连接断开）不影响消息落库。
- 消息已持久化，前端下次轮询可补拉。
- 不需要重试或异步队列。

## 10. 风险与保护

| 风险 | 保护措施 |
| --- | --- |
| 结算重试重复推送 | 幂等键 + 唯一索引 |
| 模板池为空或缺失占位符 | 兜底模板 + 渲染校验 |
| 推送太频繁 | 每结算一条、后续加每日上限 |
| 投递失败 | 不影响落库，轮询兜底补拉 |
| 多实例并发幂等冲突 | 唯一索引 + 事务保护 |

## 11. 推荐落地顺序

1. 实现 `AITemplateService.SelectAndRender(scene, userId, placeholders)`。
2. 实现 `ai_message` 表结构和索引。
3. 实现 `AIPushService.OnSettlement(event)` 基础逻辑（只处理 `win/lose`）。
4. 测试幂等性（结算重试不产生重复消息）。
5. 接入 streak 记忆更新和 `win_streak/lose_streak`。
6. 验收场景决策优先级。
7. 集成 SSE/未读接口投递。

## 12. 验收清单

- [ ] 结算推送不调用 DeepSeek。
- [ ] 同一结算事件重复投递只生成一条消息（幂等）。
- [ ] `win_streak/lose_streak` 优先于 `win/lose`。
- [ ] 模板曝光记录准确更新。
- [ ] 占位符缺失时不发送半成品文案。
- [ ] 未读消息正确标记状态为 0。
- [ ] 体力流水不被写入（`stamina_cost=0`）。
