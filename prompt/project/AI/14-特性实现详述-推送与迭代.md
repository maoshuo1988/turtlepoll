# AI 推送与迭代特性实现详述

> 本文承接 [02-特性清单.md](./02-特性清单.md)，只展开结算推送、SSE 投递、闲置推送、模板去重和后续迭代特性。基础能力详述见 [09-特性实现详述-基础能力.md](./09-特性实现详述-基础能力.md)。

## 1. 结算入账与推送事件

目标：只有用户资金入账成功后，才允许触发结算类 AI 推送。

实现方案：

1. 预测/投票结算服务先完成用户资金入账和资金流水写入。
2. 入账事务提交成功后组装 `SettlementEvent`。
3. 事件字段包含 `userId/bizType/bizId/settleResult/profitAmount/contextType/contextId/settledAt`。
4. 入账失败、事务回滚、结算待确认时不发布 AI 推送事件。
5. `AIPushService.OnSettlement` 只接收已入账事件，不再自行判断资金是否到账。

验收点：

- 入账失败不会生成 AI 推送。
- 重试结算不会绕过入账状态检查。
- 推送文案中的收益和结算结果来自已入账数据。

## 2. 结算推送幂等

目标：结算重试、消息重复投递或接口重放时，不重复生成 AI 消息。

实现方案：

1. `AIPushService.OnSettlement` 先根据事件计算候选 scene。
2. 生成稳定 `request_id`，格式建议 `settle:{bizType}:{bizId}:{scene}`。
3. 保存 `ai_message` 前检查同用户同 `request_id` 是否已存在。
4. 若已存在则跳过模板选择、消息落库和 SSE 投递。
5. 幂等检查和消息落库放在同一事务内，避免并发重复插入。

验收点：

- 同一结算事件重复触发只产生一条消息。
- 幂等命中时不增加模板曝光次数。
- 并发处理同一事件不会生成重复未读消息。

## 3. 结算记忆与 streak 维护

目标：结算事件先更新用户记忆，再用记忆结果决定是否推送连胜/连败。

实现方案：

1. 盈利结算累加 `vote_win_streak`，清零 `vote_lose_streak`。
2. 亏损结算累加 `vote_lose_streak`，清零 `vote_win_streak`。
3. 刷新 `biggest_win_amount/biggest_win_event`。
4. 刷新 `longest_win_streak/longest_lose_streak`。
5. `AIMemoryService.UpsertFlag` 记录 `flag_meta`：事件类型、业务 ID、结算时间、金额。
6. 记忆更新失败时不继续生成依赖该记忆的 streak 推送。

## 4. 结算推送场景决策

目标：同一次结算最多命中一个推送场景，避免用户收到多条相似消息。

实现方案：

1. 读取本次结算结果和更新后的 streak 记忆。
2. `vote_lose_streak >= 5` 时命中 `scene=lose_streak`。
3. `vote_win_streak >= 3` 时命中 `scene=win_streak`。
4. 盈利 `profitAmount > 0` 命中 `scene=win`。
5. 亏损 `profitAmount < 0` 命中 `scene=lose`。
6. 优先级固定为 `lose_streak > win_streak > lose > win`。
7. 未命中 scene 时不生成消息。

验收点：

- streak 场景优先于普通 win/lose。
- 盈亏为 0 或无有效 scene 时不推送。
- 同一结算最多生成一条 AI 推送。

## 5. 推送模板选择与渲染

目标：按 scene 选择可用模板，渲染为完整可展示文案。

实现方案：

1. `dialogue_template` 保存 `scene/content/enabled/weight`。
2. `AITemplateService.Select(scene,userId)` 只查启用模板。
3. MVP 可按权重随机；P1 增加未曝光优先和最少曝光优先。
4. 模板渲染替换 `{amount}`、`{n}`、`{eventName}` 等占位符。
5. 渲染后校验不存在未替换占位符。
6. 当前模板不可渲染时换下一条模板；全部失败时使用 scene 兜底文案。

## 6. 主动推送消息落库

目标：所有主动推送先保存为未读消息，再进行在线投递或离线补拉。

实现方案：

1. 保存 `ai_message`：`role=assistant`、`status=0`、`stamina_cost=0`。
2. 记录 `request_id/template_id/context_type/context_id/scene`。
3. 主动推送不调用 DeepSeek，不写 token usage。
4. 消息落库成功后写入 `template_user_view` 曝光记录。
5. 落库失败时不进行 SSE 投递。

验收点：

- 主动推送不消耗体力。
- 未读推送可按 `status=0` 查询。
- 模板曝光只在消息落库成功后增加。

## 7. SSE 投递与未读兜底

目标：在线用户即时收到推送，离线或断线用户能通过未读接口补齐。

实现方案：

1. 前端登录后建立 `GET /api/ai/pushes/stream` SSE 连接。
2. 推送落库后调用 `AIPushDelivery.Publish(userId,message)`。
3. `AIPushDelivery` 查询用户是否有在线 SSE 连接。
4. 用户在线时通过 SSE Hub 发送 `event: ai_push`。
5. 用户离线或 SSE 断开时不丢消息，等待前端调用 `GET /api/ai/pushes/unread`。
6. 前端展示或打开消息后调用 `POST /api/ai/pushes/read`。
7. 标记已读时只允许更新当前登录用户自己的 `ai_message`。

验收点：

- SSE 只负责即时通知，不作为唯一存储。
- 断线重连后未读接口能补齐期间消息。
- 已读接口不能修改其他用户消息。

## 8. presence 上报

目标：让后端能判断用户是否在线、在哪个页面停留、最近是否与 AI 互动。

实现方案：

1. 前端定期调用 `POST /api/ai/presence` 上报 `page/active`。
2. 用户进入 AI 浮窗、发送消息、关闭页面时都更新 presence。
3. `UserAIPresence` 记录 `last_seen_at/last_ai_interact_at/last_idle_push_at/idle_push_count`。
4. 服务端按用户 upsert presence，不依赖前端传用户 ID。
5. 超过在线窗口未上报时视为离线。

## 9. 闲置候选扫描与频控

目标：定时找出真正在线且达到闲置条件的用户，并限制推送频率。

实现方案：

1. cron 每分钟触发 `AIPresenceService.FindIdleCandidates`。
2. 候选必须 `active=true` 且 `last_seen_at` 在在线窗口内。
3. `now - last_ai_interact_at >= idleTriggerMinutes` 才进入推送判断。
4. 检查 `last_idle_push_at` 是否超过冷却时间。
5. 检查当日 `idle_push_count` 是否低于 `aiChat.idlePushDailyLimit`。
6. 未通过任一条件时跳过用户，不写消息。

## 10. 闲置记忆选择与消息生成

目标：用户在线闲置时，用已有记忆生成一条轻量提醒。

实现方案：

1. 读取 `user_ai_memory` 中可用于 idle 的 Flag。
2. 优先选择有事实、有模板、近期未推过的记忆。
3. 可用场景包括 `biggest_win_amount/first_egg_turtle/longest_win_streak`。
4. 使用 `AITemplateService` 渲染 idle 文案。
5. 模板缺少必要数据或渲染失败时跳过本用户。
6. 渲染成功后复用主动推送消息落库和 SSE/未读兜底链路。

## 11. 闲置推送状态回写

目标：闲置推送成功后更新计数和记忆元数据，避免短期重复。

实现方案：

1. 消息落库成功后更新 `last_idle_push_at`。
2. 当日 `idle_push_count + 1`。
3. 将被使用记忆的 `flag_meta.lastPushedAt` 更新为当前时间。
4. 状态回写和消息落库尽量放在同一事务内。
5. 状态回写失败时不投递 SSE，避免用户看到但后端未记账。

## 12. 模板去重选择

目标：避免用户短期反复看到同一句。

实现方案：

1. 每次主动推送成功后 upsert `template_user_view`。
2. `view_count + 1`，更新 `last_viewed_at`。
3. 选择模板时按未曝光、最少曝光、权重随机排序。
4. 可选：同一 scene 在 24 小时内不重复同一 template。

## 13. 后续迭代

流式输出：

1. DeepSeekClient 增加 SSE 读取模式。
2. `POST /api/ai/chat/stream` 或同接口通过参数 `stream=true` 开启。
3. 流结束后再保存完整助手消息和 token usage。
4. 中途失败时保存 partial 状态或不保存，根据产品口径决定。

Tool Calls：

1. 定义工具白名单：查询预测市场、查询我的余额、查询赛程状态。
2. 工具参数必须 JSON Schema 校验。
3. 模型只返回 tool call，服务端执行真实查询。
4. 所有工具只读，禁止下注、扣款、修改数据。

后台模板管理：

1. 新增后台接口：模板列表、创建、编辑、启停、权重调整。
2. 校验 scene 是否在枚举内。
3. 校验模板占位符是否符合 scene 要求。
4. 记录操作日志，可按 scene 预览渲染效果。

运营类推送：

1. 定义生日、注册周年、首次盈利、收集数量里程碑等事件。
2. 定时任务或业务事件触发 `AIPushService`。
3. 复用模板池和未读消息机制。
4. 受每日推送上限和冷却期控制。
