# 主动推送实现设计

> 本文说明 AI 主动推送能力如何落地。主动推送只使用站内业务事件和模板池，不实时调用 DeepSeek，不消耗 AI 体力。

## 1. 目标与边界

- 结算后生成赢、输、连胜、连败小龟文案。
- 用户在线闲置时生成记忆类提醒。
- 在线用户通过 SSE 接收即时推送。
- 前端可以轮询未读推送并标记已读，作为 SSE 断线和离线期间的兜底。

- 主动推送不调用 LLM。
- 主动推送不消耗 `user_ai_stamina`。
- 推送内容必须来自 `dialogue_template` 或固定兜底模板。
- 每个业务事件最多生成一条推送。
- 不能向 LLM 或前端暴露其他用户的下注明细。

## 2. 服务拆分

| 服务 | 职责 |
| --- | --- |
| `AIPushService` | 接收业务事件，判断推送场景，保存未读消息，控制幂等和频率。 |
| `AITemplateService` | 按 scene 选择模板、渲染占位符、记录曝光。 |
| `AIMemoryService` | 更新和读取 `user_ai_memory`，维护 win/lose streak 和记忆事实。 |
| `AIPresenceService` | 记录用户在线状态，扫描闲置候选用户。 |
| `AIPushDelivery` | 投递层抽象，优先用 SSE 投递，未读轮询兜底。 |

`AIPushDelivery` 推荐做成 `Deliver(userId int64, message AIMessage) error` 接口。MVP 可先 no-op + 未读轮询；即时体验直接接 SSE，不优先上 WebSocket。协议细节见 [11-前端推送协议设计.md](./11-前端推送协议设计.md)。

## 3. 数据落点

### 3.1 ai_message

主动推送保存为一条助手消息：

```text
role=assistant
scene=win / lose / win_streak / lose_streak / idle_biggest_win ...
content=渲染后的文案
template_id=使用的模板 ID
status=0
stamina_cost=0
context_type=predict_market / pet / none
context_id=业务对象 ID
request_id=业务幂等键
```

`status`：`0` 未读，`1` 已读。主动推送必须写非空 `request_id`。
- `ai_message` 建议加唯一索引 `uniq_ai_message_user_request(user_id, request_id)`；普通聊天消息 `request_id` 可为空。

### 3.2 dialogue_template

模板字段至少需要：`scene/content/enabled/weight`。

### 3.3 template_user_view

每次推送成功后记录 `user_id/template_id/view_count/last_viewed_at`，用于优先选择未看过或看得最少的模板。建议加唯一索引 `uniq_template_user_view(user_id, template_id)`，曝光记录使用 upsert 更新。

## 4. 结算推送

### 4.1 事件输入

结算服务在用户单据完成结算后调用 `AIPushService.OnSettlement(event)`。

事件建议字段：

```text
event_id            唯一事件 ID，如 predict:settle:{betId}
user_id
biz_type            predict / vote / pk / battle
biz_id              betId 或结算项 ID
context_type        predict_market
context_id          marketId
profit_amount       正数盈利，负数亏损，0 表示不推
settle_result       win / lose / refund / canceled
event_title         用于模板占位符，可选
settled_at
```

### 4.2 处理流程

```text
结算服务完成资金入账
  -> AIPushService.OnSettlement(event)
  -> 开启事务
  -> 幂等检查 request_id 是否已存在
  -> AIMemoryService.UpdateSettlementMemory(event)
       - 更新 vote_win_streak / vote_lose_streak
       - 更新 biggest_win_amount / biggest_win_event
       - 更新 longest_win_streak
  -> DecideSettlementScene(event, memory)
  -> AITemplateService.Render(scene, userId, placeholders)
  -> 保存 ai_message(status=unread, stamina_cost=0)
  -> 写 template_user_view
  -> 提交事务
  -> AIPushDelivery.Deliver(userId, message)
```

流程图见 [12-主动推送流程图.md#1-结算推送流程](./12-主动推送流程图.md#1-结算推送流程)。

### 4.3 场景决策

一次结算最多推一条：

| 优先级 | 条件 | scene |
| --- | --- | --- |
| 1 | `vote_lose_streak >= 5` | `lose_streak` |
| 2 | `vote_win_streak >= 3` | `win_streak` |
| 3 | `profit_amount < 0` | `lose` |
| 4 | `profit_amount > 0` | `win` |
| - | 平局、退款、作废 | 不推送 |

- streak 推送优先于普通输赢。
- `profit_amount` 用真实结算净收益口径，不能用下注本金代替。
- 若同一个用户一天结算很多单，仍建议结算类推送每单最多一条，但可后续加每日上限。

### 4.4 幂等键

`ai_message.request_id` 建议 `settle:{bizType}:{bizId}:{scene}`。保存前先查 `where user_id=? and request_id=?`，存在则直接跳过。

并发要求：

- 幂等检查和 `ai_message` 插入必须在同一事务内。
- 仍以唯一索引兜底处理并发插入；命中唯一冲突时按幂等成功处理，不再投递。
- 记忆更新、消息落库、模板曝光写入一起提交；事务提交成功后再做 SSE 投递。

## 5. 闲置推送

### 5.1 presence 上报

前端定期调用 `POST /api/ai/presence`。

请求：

```json
{
  "page": "predict_market",
  "active": true
}
```

服务端更新 `user_ai_presence.first_seen_at/last_seen_at/page/active`；用户主动聊天成功时同步更新 `last_ai_interact_at=now`。

### 5.2 扫描条件

定时任务每分钟扫描：

```text
active=true
now - last_seen_at <= 60 秒
now - last_ai_interact_at >= aiChat.idleTriggerMinutes
now - last_idle_push_at >= aiChat.idlePushCooldownMinutes
idle_push_count_date != today 或 idle_push_count < aiChat.idlePushDailyLimit
```

默认配置：`idleTriggerMinutes=10`、`idlePushCooldownMinutes=120`、`idlePushDailyLimit=2`。

### 5.3 记忆选择

候选场景：

| memory flag | scene | 占位符 |
| --- | --- | --- |
| `biggest_win_amount` + `biggest_win_event` | `idle_biggest_win` | `{amount}`、`{event}` |
| `first_egg_turtle` | `idle_first_egg` | `{turtle_name}` |
| `longest_win_streak` | `idle_longest_streak` | `{n}` |

1. 只选择用户已有事实的场景。
2. 优先选择最近未推过的场景。
3. 同场景冷却期内不重复推。
4. 没有可用记忆时跳过，不发送空泛闲聊。

最近推送场景可以先放在 `user_ai_memory.flag_meta.lastPushedAt`，后续再拆独立日志表。

### 5.4 闲置推送流程

```text
cron 每分钟触发
  -> AIPresenceService.FindIdleCandidates()
  -> 对每个用户读取 user_ai_memory
  -> DecideIdleScene(memory, recentPushMeta)
  -> AITemplateService.Render(scene, userId, placeholders)
  -> 开启事务
  -> 保存 ai_message(status=unread, stamina_cost=0)
  -> 更新 user_ai_presence.last_idle_push_at / idle_push_count
  -> 更新 memory flag_meta.lastPushedAt
  -> 写 template_user_view
  -> 提交事务
  -> AIPushDelivery.Deliver(userId, message)
```

流程图见 [12-主动推送流程图.md#2-闲置推送流程](./12-主动推送流程图.md#2-闲置推送流程)。

## 6. 模板选择与渲染

### 6.1 选择算法

```text
templates = enabled templates by scene
left join template_user_view by userId
sort by:
  has_viewed asc
  view_count asc
  random weighted by weight
limit 1
```

如果数据库层做加权随机不方便，可在服务层先取最少曝光的一组模板，再按 `weight` 计算随机区间。

### 6.2 占位符校验

渲染前声明每个 scene 允许的占位符：

| scene | 必填占位符 |
| --- | --- |
| `win` | `{amount}` |
| `lose` | `{amount}` |
| `win_streak` | `{n}` |
| `lose_streak` | `{n}` |
| `idle_biggest_win` | `{amount}`、`{event}` |
| `idle_first_egg` | `{turtle_name}` |
| `idle_longest_streak` | `{n}` |

渲染后检查是否仍存在 `{xxx}`；若存在则跳过该模板并尝试下一条，全部失败时使用固定兜底模板。

## 7. 未读接口

### 7.1 拉取未读

```text
GET /api/ai/pushes/unread
```

查询：

```text
where user_id=? and role=assistant and status=0 and scene in pushScenes
order by create_time asc, id asc
limit 20
```

返回：

```json
{
  "results": [
    {
      "id": 20001,
      "scene": "win_streak",
      "content": "3 连了。我都怀疑是不是出 bug 了。",
      "contextType": "predict_market",
      "contextId": 123,
      "createTime": 1760000000
    }
  ]
}
```

### 7.2 标记已读

```text
POST /api/ai/pushes/read
```

请求：

```json
{
  "ids": [20001, 20002]
}
```

处理：

```text
update ai_message
set status=1
where user_id=? and id in (?) and role=assistant
```

只能标记当前登录用户自己的消息。

响应：

```json
{
  "updated": 2
}
```

`updated` 表示本次真实从未读改为已读的消息数；重复提交已读 ID 时返回 0 或较小值，不视为错误。

## 8. 风险与保护

| 风险 | 保护 |
| --- | --- |
| 结算重试重复推送 | `request_id` 幂等。 |
| 模板池为空 | 使用固定兜底模板或跳过。 |
| 模板占位符缺失 | 渲染后校验，失败换模板。 |
| 推送太频繁 | 闲置冷却、每日上限、每次结算最多一条。 |
| 用户离线仍收到闲置推送 | 闲置推送只扫描在线用户。 |
| 前端轮询漏消息 | 消息先落库，再投递；轮询以库为准。 |
| SSE 投递失败 | 不影响消息落库，前端下次轮询补拉。 |
| 多实例部署 SSE 无法跨进程投递 | MVP 单实例用本机 Hub；多实例上线前接 Redis Pub/Sub，见 [11-前端推送协议设计.md](./11-前端推送协议设计.md)。 |

## 9. 推荐落地顺序

1. 实现 `AITemplateService.SelectAndRender`。
2. 实现未读推送接口：`GET /api/ai/pushes/unread`、`POST /api/ai/pushes/read`。
3. 实现结算推送 `AIPushService.OnSettlement`，先接 `win/lose`。
4. 接入 streak 记忆更新和 `win_streak/lose_streak`。
5. 实现 `POST /api/ai/presence` 和在线状态更新。
6. 增加闲置扫描 cron，生成 idle 推送。
7. 实现 `GET /api/ai/pushes/stream` SSE 即时投递。
8. 多实例部署时接入跨进程 Pub/Sub。

## 10. 验收清单

- 结算推送不调用 DeepSeek。
- 同一个结算事件重复投递只生成一条消息。
- `win_streak/lose_streak` 优先于普通 `win/lose`。
- 模板曝光记录会更新。
- 未读推送只能被当前用户拉取和标记已读。
- 闲置推送遵守冷却期和每日上限。
- 模板缺失或占位符不完整时不会发送半成品文案。
- SSE 在线时能收到 `ai_push` 事件。
- SSE 断线后能通过 `Last-Event-ID` 或未读接口补齐遗漏消息。
