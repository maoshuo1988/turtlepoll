# 预测市场公共部分特性详情介绍

## 1. 用户预测战绩

### 1.1 目标

为每个用户维护跨来源预测市场的统一战绩：

- 下注胜率。
- 最新连胜场数。
- 可用于排行榜、个人主页、用户卡片展示。

统计范围覆盖世界杯预测市场和 Polymarket 预测市场。来源专项只负责写入市场结果，战绩更新由公共用户结算链路触发。

### 1.2 统计口径

胜率按“市场场次”统计，不按下注单条数统计。

同一用户在同一市场可能有多笔下注：

- 只统计为一场。
- 同一市场只在该用户首次完成该市场结算时更新一次战绩。
- 若该用户在同一市场下注多个选项，按该市场下所有下注单的净结果归并。

市场级用户结果：

| 结果 | 口径 |
|------|------|
| `WIN` | 至少一笔命中且总派奖大于 0 |
| `LOSE` | 没有命中，或总派奖为 0 |
| `VOID` | 市场作废或退款，不计入胜率与连胜 |

胜率公式：

```text
winRate = winMarketCount / settledMarketCount
```

其中 `settledMarketCount` 只包含 `WIN/LOSE`，不包含 `VOID`。

### 1.3 最新连胜场数

最新连胜场数表示用户最近连续命中的市场场次数。

更新规则：

- 当前市场结算结果为 `WIN`：`currentWinStreak += 1`。
- 当前市场结算结果为 `LOSE`：`currentWinStreak = 0`。
- 当前市场结算结果为 `VOID`：不改变 `currentWinStreak`。

为避免重复结算导致连胜重复增长，必须通过 `userId + marketId` 幂等记录控制。

### 1.4 写入时机

用户调用公共结算接口时更新：

```text
POST /api/coin/settle
  -> 结算当前用户在该 market 下的 OPEN 下注单
  -> 归并本次 market 用户结果
  -> 幂等写入用户市场战绩
  -> 增量更新用户预测统计
```

运营人工结算或自动结算只写 `PredictMarket.result/status`，不直接更新用户战绩。只有用户领取结算时才更新该用户战绩。

### 1.5 重算能力

如果未来支持运营重置结果或纠错，需要提供异步重算能力：

- 按用户重算。
- 按市场重算影响用户。
- 重算基于 `PredictUserMarketStat` 明细或 `PredictBet` 历史。

P0 可先实现增量更新，P1 补充重算任务和审计日志。

## 2. 账户余额榜

### 2.1 账户余额 Top N 排序

目标：快速查询账户余额最高的前 N 名用户。

排序来源：

- `UserCoin.balance`
- `UserCoin.userId`

默认排序：

```text
balance desc
userId asc
```

`userId asc` 用于余额相同时稳定排序。

查询约束：

- `limit` 默认 20。
- `limit` 最大 100。
- 只返回账户存在的用户。

推荐索引：

```text
index UserCoin(balance desc, user_id)
```

### 2.2 榜单用户资料聚合

目标：为 Top N 用户补齐展示资料。

返回字段：

- 用户名称。
- 用户头像。

数据来源：

- `User.nickname`
- `User.avatar`

聚合方式：

- 先按余额查询 Top N `userId`。
- 再批量读取用户资料。
- 保持 Top N 原排序，不按昵称或头像重新排序。

### 2.3 榜单预测战绩聚合

目标：为 Top N 用户补齐预测市场战绩。

返回字段：

- 用户胜率。
- 用户最新连胜场次。

数据来源：

- `winRate`
- `currentWinStreak`

未参与过预测市场的用户：

- `winRate = 0`
- `currentWinStreak = 0`

聚合方式：

- 批量读取 `PredictUserStat`。
- 不实时扫描 `PredictBet`。
- 不实时重算胜率。

### 2.4 我的余额与排名摘要

目标：排行榜接口同时返回当前登录用户的排名和余额。

返回字段：

- `myRank`
- `myBalance`
- `myWinRate`
- `myCurrentWinStreak`

口径：

- `myBalance` 来自当前用户 `UserCoin.balance`。
- `myRank` 按余额榜同一排序规则计算。
- 未登录用户可返回空摘要，或要求登录后访问。
- 当前用户没有金币账户时，`myBalance = 0`，`myRank = null`。

排名计算：

```text
rank = count(balance greater than myBalance) + count(balance equals myBalance and userId less than myUserId) + 1
```

如果当前用户没有账户记录，不参与排名。

### 2.5 性能要求

排行榜需要快速查询，不能每次实时扫描所有下注单。

推荐实现：

- `UserCoin.balance` 建索引。
- 用户预测统计单独物化到 `PredictUserStat`。
- 查询时从 `UserCoin` 取 Top N，再按 `userId` 批量关联 `User` 和 `PredictUserStat`。
- 我的排名用计数查询，不扫描全部用户后在内存排序。

## 3. 双结算口径

预测市场公共部分有两套结算，使用不同奖池，互不替代。

### 3.1 下注结算

目标：根据市场最终结果结算用户下注盈亏。

规则：

- 仅在 `PredictMarket.status = SETTLED` 后允许用户领取结算。
- 只结算当前用户该市场下尚未结算的 `OPEN` 下注单。
- 命中结果则按锁定赔率派奖，未命中则 `payout = 0`。
- 结算成功后同步更新用户战绩：胜率、连胜、市场级明细。
- 下注结算不依赖开撕台评论热度，也不消耗开撕台铸币预算。

奖池口径：

```text
下注结算奖池 = 预测市场的奖池
```

### 3.2 撕裂带结算

目标：基于胜方评论热度进行系统铸币发放。

规则：

- 仅在预测市场结算后 1 小时内发放。
- 按胜方阵营的一级评论热度与回复热度聚合到用户维度。
- 点赞热度仅进入快照和榜单，不进入发币分子分母。
- 发放结果必须写金币流水和奖励审计记录。

奖池口径：

```text
撕裂带结算奖池 = 用户评论热度 / 总评论热度 * 预测市场奖池 * 10%
```

说明：

- 这部分属于系统铸币发放。
- `预测市场奖池` 仅指单个市场的真实池。
- `10%` 是系统发放系数，不是下注派奖系数。

### 3.3 结算关系

- 下注结算与撕裂带结算由同一市场状态触发，但使用不同奖池。
- 下注结算影响用户资金和战绩。
- 撕裂带结算只影响评论奖励发币与审计，不影响用户下注胜率。
- 两者都必须幂等，但幂等键不同：下注结算按用户+市场，撕裂带结算按市场+奖励批次。

## 4. 开撕台评论奖励

### 4.1 预测市场评论选项绑定

目标：用户对预测市场发表评论或回复时，记录该互动支持的预测选项。

现有 `Comment` 只记录 `entityType/entityId/content/userId`，不能表达评论属于 `A/B/DRAW` 哪一方。因此需要新增预测评论元数据。

建议：

- 预测市场一级评论必须提交 `marketId` 和 `option`。
- 预测市场回复评论必须提交 `marketId`；`option` 为可选字段，仅未锁边场景可传，作为弱锁边输入，并写入最终 `option_at_action`。
- `option` 必须符合 `PredictMarket.marketType`。
- 评论或回复创建成功后写入 `PredictCommentMeta`（或等价互动元数据）。

回复 `option_at_action` 推导顺序：

- 用户已有锁边时，优先使用锁边 `option`。
- 用户未锁边且请求传入 `option` 时，使用请求 `option`。
- 前两者都不可用时，回退父评论归属。

`option` 口径：

| 市场类型 | 合法评论选项 |
|----------|--------------|
| `binary` | `A/B` |
| `1x2` | `A/B/DRAW` |

### 4.2 胜方评论与回复用户筛选

市场结算后，系统按 `PredictMarket.result` 筛选胜方评论与回复用户。

筛选条件：

- `Comment.entityType` 为预测市场一级评论或预测市场评论回复。
- `Comment.entityId = marketId`（一级评论）或父评论属于 `marketId`（回复评论）。
- `Comment.status` 为正常。
- `PredictCommentMeta.option = PredictMarket.result`。
- 评论创建时间早于奖励任务执行时间。

用户去重：

- 同一用户同一市场可有多条评论与回复，但奖励按热度聚合到用户维度。
- 同一用户在同一市场同时评论多个选项时，仅统计与胜方一致的热度。

### 4.3 奖金池与热度权重分配

开撕台评论奖励采用固定公式：

```text
用户获得奖励 = 用户评论热度 / 总评论热度 * 预测市场奖池 * 10%
```

其中：

- 用户评论热度：该用户在胜方阵营的一级评论热度 + 回复热度。
- 总评论热度：所有用户在胜方阵营的一级评论热度 + 回复热度。
- 预测市场奖池：单个市场的真实池。
- 10%：系统铸币系数。

固定规则：

```text
当 总评论热度 <= 0 时，不发放奖励，记录 EMPTY_HEAT
用户奖励向下取整到最小货币单位
分配余数写入 remainder 字段并记录审计
```

- 点赞行为仅影响点赞热度项和榜单，不直接进入奖励公式。

### 4.4 回复评论与点赞热度累计

回复评论热度：

```text
replyHeat 与 commentHeat 使用同一评论热度口径
均计入用户评论热度与总评论热度
```

点赞热度：

```text
每用户对同一评论目标最多点赞 1 次
取消点赞不回滚历史热度
点赞热度仅用于榜单与快照
```

### 4.5 结算后一小时发放窗口

奖励必须在预测市场结算后 1 小时内发放。

触发方式建议：

- 市场写入 `SETTLED` 后，设置 `commentRewardDeadline = settledAt + 3600`。
- 定时任务每分钟扫描待发放市场。
- 条件满足时立即发放，不等待用户领取个人结算。

扫描条件：

```text
status = SETTLED
commentRewardStatus = PENDING
now <= commentRewardDeadline
```

如果超过 1 小时仍未发放：

- 标记为 `EXPIRED`。
- 不再自动发放。
- 记录过期原因，供运营人工处理。

### 4.6 评论奖励发放审计

奖励发放必须可审计。

至少记录：

- `marketId`
- `winnerOption`
- `bonusPool`
- `winnerTotalCommentHeat`
- `remainder`
- `status`
- `reason`
- `settledAt`
- `deadlineAt`
- `paidAt`

每个获奖用户还需要记录：

- `userId`
- `amount`
- `userCommentHeat`
- `firstCommentId`
- `UserCoinLog.id`

金币流水：

```text
UserCoinLog.bizType = COMMENT_REWARD
UserCoinLog.bizId = PredictCommentRewardLog.id
UserCoinLog.amount > 0
```

### 4.7 幂等与并发

幂等要求：

- 同一 `marketId` 只能有一条奖励批次记录。
- 同一 `rewardLogId + userId` 只能有一条奖励明细。
- 同一用户同一市场只发一次奖励。

并发要求：

- 发放任务需要锁定 `PredictMarket` 或 `PredictCommentRewardLog`。
- 发放状态从 `PENDING` 变为 `PROCESSING` 后才开始写金币。
- 任务失败时标记 `FAILED`，允许运营重试。

### 4.8 与用户结算的关系

开撕台评论奖励独立于用户下注结算：

- 用户不需要下注也可以因胜方评论或回复获得奖励。
- 用户是否调用 `/api/coin/settle` 不影响开撕台评论奖励发放。
- 开撕台评论奖励不会影响 `PredictBet.payout`。
- 开撕台评论奖励不会计入用户下注胜率。

- 本文不再保留“冲突说明与处置”类描述。

## 5. 强弱锁边机制

### 5.1 目标

为预测市场评论、回复、点赞和下注提供统一的阵营归属约束，支持强锁边与弱锁边并存。

### 5.2 锁边类型

| 锁边类型 | 触发入口 | 语义 | 覆盖关系 |
|------|------|------|------|
| `INTERACT` | 评论、回复、点赞 | 弱锁边 | 可被 `BET` 覆盖 |
| `BET` | 下注 | 强锁边 | 覆盖同一目标上的 `INTERACT` |

### 5.3 建立规则

- 首次互动且无锁边时，建立 `INTERACT` 弱锁边。
- 首次下注且无锁边时，建立 `BET` 强锁边。
- 已有 `INTERACT` 弱锁边时，若下注选项一致则升级为 `BET`，否则以 `BET` 覆盖并拒绝冲突请求。
- 已有 `BET` 强锁边时，后续任何不一致的互动或下注都直接拒绝。

### 5.4 覆盖规则

- `BET` 的优先级高于 `INTERACT`。
- 同一用户、同一市场、同一阵营下，`BET` 会覆盖该用户此前的 `INTERACT` 归属。
- 同一用户、同一市场、不同阵营下，`BET` 不允许覆盖为新阵营，直接返回 `TEAR_CAMP_LOCKED_BY_BET`。

### 5.5 适用范围

- 预测市场一级评论。
- 预测市场回复评论。
- 预测市场点赞。
- 预测市场下注。
