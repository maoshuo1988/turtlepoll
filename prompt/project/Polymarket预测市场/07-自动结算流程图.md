# Polymarket自动结算流程图

> 本文只描述流程闭环，不写代码。目标是说明每个市场从数据拉取到最终结算，必须落到明确状态：可下注、已封盘、已自动结算、待运营处理或取消处理。

## 1. 总闭环

```mermaid
flowchart TD
  subgraph Discovery[Discovery 发现轮巡：创建与登记]
    A[定时触发 Discovery] --> B[拉取 Gamma tags/markets]
    B --> C{市场是否在配置范围内}
    C -- 否 --> C1[跳过]
    C -- 是 --> D[upsert PredictMarket]
    D --> E[upsert PredictContext]
    E --> F[upsert Outcome 映射]
    F --> T[登记 externalMarketId 到 Tracking 表]
  end

  subgraph Tracking[Tracking 状态轮巡：按 ID 闭环]
    U[定时触发 Tracking] --> V[读取 Tracking 表中待跟踪 ID]
    V --> W[按 market ID 精确拉取]
    W --> X[upsert 最新 market/outcomes]
    X --> G{市场是否 resolved}
  end

  T -. 后续周期被读取 .-> V
  G -- 否 --> H{是否已到 closeTime 或 closed=true}
  H -- 否 --> I[状态 OPEN]
  H -- 是 --> J[状态 CLOSED]
  G -- 是 --> K[识别外部赢家]
  K --> L{赢家是否唯一}
  L -- 否 --> M[状态 CLOSED + 记录待运营]
  L -- 是 --> N[赢家映射为站内 A/B]
  N --> O{映射是否唯一有效}
  O -- 否 --> M
  O -- 是 --> P[写 result=A/B status=SETTLED]
  P --> Q[用户调用 /api/coin/settle]
  Q --> R[按锁定赔率派奖]
  M --> S[运营补映射或人工结算]
  S --> P
```

闭环要求：

- Discovery 和 Tracking 是两个独立轮巡，不要求同一次任务串行完成。
- Discovery 只保证发现、创建、登记 externalMarketId。
- Tracking 只按已登记 externalMarketId 精确拉取，并负责推进状态与结算闭环。
- 未开始且可下注：`OPEN`
- 已封盘但未有结果：`CLOSED`
- 有明确结果：`SETTLED`
- 有外部结果但无法映射：`CLOSED + 待运营`
- 取消/无效：不进入自动派奖，进入取消处理或运营处理

## 2. 数据拉取流程

双轮巡调度关系：

```mermaid
flowchart LR
  A[Discovery Cron] --> B[按 tag/slug 拉取一批市场]
  B --> C[过滤配置范围]
  C --> D[创建或更新站内市场]
  D --> E[(Tracking 表 externalMarketId)]

  F[Tracking Cron] --> G[分页读取 Tracking 表]
  G --> E
  E --> H[按 externalMarketId 精确拉取]
  H --> I[更新外部状态]
  I --> J{是否可结算}
  J -- 否 --> K[更新 OPEN/CLOSED/待运营]
  J -- 是 --> L[写 result/status=SETTLED]
```

要点：

- Discovery 可按 tag/slug 分页拉取，每次只处理一批，比如 50 个。
- Discovery 发现到的 market ID 必须持久化，不能只依赖下一次 tag 分页再次出现。
- Tracking 每轮从已持久化 ID 中取一批处理，保证 market ID `99` 这类已登记市场后续能被继续跟踪。
- 自动结算触发点在 Tracking，不在 Discovery。

```mermaid
sequenceDiagram
  participant Cron as Discovery
  participant Sync as PolymarketSyncService
  participant Gamma as Gamma API
  participant DB as PostgreSQL

  Cron->>Sync: DiscoveryPoller()
  Sync->>Gamma: GET /tags
  Gamma-->>Sync: tags
  Sync->>Sync: configured tag slug/name/id -> Gamma tag_id
  loop configured tags
    Sync->>Gamma: GET /markets/keyset?tag_id=...&limit=discoveryPageSize
    Gamma-->>Sync: markets page
    Sync->>DB: upsert market/context/outcomes/tracking
  end
  loop configured marketSlugs
    Sync->>Gamma: GET /markets/keyset?limit=discoveryPageSize
    Gamma-->>Sync: markets page
    Sync->>Sync: local slug filter
    Sync->>DB: upsert market/context/outcomes/tracking
  end
```

Tracking 精确拉取：

```mermaid
sequenceDiagram
  participant Cron as Tracking
  participant Sync as PolymarketSyncService
  participant Gamma as Gamma API
  participant DB as PostgreSQL

  Cron->>Sync: TrackingPoller()
  Sync->>DB: query tracking rows
  loop each externalMarketId
    Sync->>Gamma: GET /markets/{id}
    Gamma-->>Sync: market detail
    Sync->>DB: upsert latest market/outcomes
    Sync->>DB: update tracking status
  end
```

实现约束：

- `tags` 和 `marketSlugs` 只决定同步范围。
- 每个同步到的 market 必须执行 upsert。
- upsert 后必须进入状态判定，不允许停在未知状态。

## 3. 市场状态判定

```mermaid
flowchart TD
  A[读取 Gamma market] --> B{resolved=true}
  B -- 是 --> C[进入赢家识别]
  B -- 否 --> D{closed=true 或 closeTime<=now}
  D -- 是 --> E[PredictMarket.status=CLOSED]
  D -- 否 --> F[PredictMarket.status=OPEN]
  C --> G{winner 可唯一识别并映射 A/B}
  G -- 是 --> H[PredictMarket.status=SETTLED result=A/B]
  G -- 否 --> I[PredictMarket.status=CLOSED result='' resolved=true]
  I --> J[记录待运营原因]
```

状态不变量：

| 场景 | status | result | 用户能否下注 | 用户能否结算 |
|------|--------|--------|--------------|--------------|
| 未封盘 | `OPEN` | 空 | 能 | 不能 |
| 已封盘未出结果 | `CLOSED` | 空 | 不能 | 不能 |
| resolved 但无法映射 | `CLOSED` | 空 | 不能 | 不能 |
| resolved 且映射明确 | `SETTLED` | `A/B` | 不能 | 能 |

## 4. Outcome 映射流程

```mermaid
flowchart TD
  A[Gamma market.outcomes] --> B{outcome 数量是否为 2}
  B -- 否 --> C[不生成默认映射]
  B -- 是 --> D{站内是否已有映射}
  D -- 是 --> E[保留已有映射]
  D -- 否 --> F[outcome 0 映射为 A]
  F --> G[outcome 1 映射为 B]
  E --> H[用于赢家映射]
  G --> H
  C --> I[进入运营待处理]
```

映射保护：

- 默认映射只用于二元市场。
- 已有映射不被同步覆盖。
- 运营校正后的映射优先级最高。
- 没有映射时不自动结算。

## 5. 赢家识别流程

```mermaid
flowchart TD
  A[Gamma market resolved] --> B{是否取消/无效}
  B -- 是 --> C[进入取消/无效处理]
  B -- 否 --> D{outcome 是否有 winner 标记}
  D -- 是 --> E[使用 winner outcome]
  D -- 否 --> F{resolution 是否匹配 outcome name}
  F -- 是 --> E
  F -- 否 --> G{resolution 是否匹配 outcome id/token}
  G -- 是 --> E
  G -- 否 --> H[NO_WINNER 待运营]
  E --> I{映射表是否唯一匹配 A/B}
  I -- 是 --> J[自动 SETTLED]
  I -- 否 --> K[NO_OUTCOME_MAPPING 待运营]
```

禁止规则：

- 禁止用 `outcomePrices` 单独判断赢家。
- 禁止用标题模糊匹配赢家。
- 禁止把所有 `Yes` 固定视为 A，必须通过映射表。

## 6. 用户结算流程

```mermaid
sequenceDiagram
  participant User as User
  participant API as /api/coin/settle
  participant DB as PostgreSQL
  participant Coin as UserCoinService
  participant AI as AIPushService

  User->>API: POST marketId
  API->>DB: lock PredictMarket
  DB-->>API: status/result
  API->>API: require status=SETTLED result=A/B
  API->>DB: lock user's OPEN bets
  loop each bet
    API->>API: option == result ?
    API->>DB: update PredictBet SETTLED
    API->>Coin: payout or 0
  end
  API->>AI: settlement push event
  API-->>User: settlement result
```

资金不变量：

- 自动结算只写市场结果，不直接派奖。
- 用户派奖只发生在 `/api/coin/settle`。
- `PredictBet.status=SETTLED` 后重复调用不会重复派奖。

## 7. 运营兜底流程

```mermaid
flowchart TD
  A[自动结算失败] --> B[记录 reason]
  B --> C[进入待运营查询]
  C --> D{运营判断}
  D -- 补 outcome 映射 --> E[保存映射]
  E --> F[重跑同步]
  F --> G[自动 SETTLED]
  D -- 直接人工结算 --> H[POST /api/admin/predict/market/settle]
  H --> I[SETTLED]
  D -- 取消/无效 --> J[取消或退款流程]
```

待运营查询最小条件：

```text
sourceModel = Polymarket
resolved = true
status = CLOSED
result = ''
```

失败 reason：

| reason | 说明 | 闭环动作 |
|--------|------|----------|
| `NO_WINNER` | 外部没有可识别赢家 | 运营确认结果 |
| `NO_OUTCOME_MAPPING` | winner 找不到 A/B 映射 | 补映射 |
| `AMBIGUOUS_OUTCOME` | 匹配到多个 outcome | 人工确认 |
| `INVALID_MARKET_TYPE` | 非二元市场 | 人工处理 |
| `CANCELLED_OR_INVALID` | 外部取消/无效 | 退款或作废 |

## 8. 每个市场必须落入的终态

```mermaid
stateDiagram-v2
  [*] --> OPEN: 未封盘
  OPEN --> CLOSED: 到 closeTime 或 closed=true
  CLOSED --> SETTLED: resolved + 映射明确
  CLOSED --> OPS_PENDING: resolved + 映射失败
  OPS_PENDING --> SETTLED: 运营补映射/人工结算
  OPS_PENDING --> CANCELLED: 运营确认取消/无效
  SETTLED --> [*]
  CANCELLED --> [*]
```

终态定义：

- `SETTLED`：用户可结算，资金闭环完成。
- `CANCELLED`：进入退款或作废流程，不能派奖。
- `OPS_PENDING`：不是数据库最终状态，表示运营查询视图中的待处理集合。

数据库当前没有 `CANCELLED` 市场状态；落地前需要先决定是新增状态，还是用 `CLOSED + issue reason` 表示。

## 9. 验收口径

- 每次同步后的 Polymarket 市场不允许停留在未知状态。
- resolved 且映射明确的市场必须自动 `SETTLED`。
- resolved 但映射失败的市场必须能被运营查询出来。
- 自动结算不能覆盖已人工结算的 `result`。
- 自动结算不能直接修改用户余额。
- 用户重复结算不能重复派奖。
- 取消/无效市场不能自动走 WIN/LOSE 派奖。
