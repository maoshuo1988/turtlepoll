## 3. 配置

配置文件：`bbs-go.yaml`。

启动时读取顺序：

- 服务默认读取当前工作目录下的 `bbs-go.yaml`。
- 如果当前工作目录没有该文件，会继续尝试读取可执行文件同目录下的 `bbs-go.yaml`。
- 首次部署可从 `bbs-go.example.yaml` 复制生成，生产环境已有 `bbs-go.yaml` 时不要用示例文件覆盖。
- 当前代码默认文件名是 `bbs-go.yaml`；如果手上文件名是 `bbs-go.yml`，需要改名为 `bbs-go.yaml`。

启动命令示例：

```bash
BBSGO_ENV=prod ./bbs-go-server
```

本地开发从仓库根目录启动即可读取根目录下的 `bbs-go.yaml`：

```bash
BBSGO_ENV=prod go run ./main.go
```

### 3.1 最小配置

```yaml
footballData:
  apiKey: "YOUR_FOOTBALL_DATA_API_KEY"
  competitionCode: "WC"
  season: 2026
  cronSpec: "0 */6 * * *"
```

字段说明：

| 字段 | 说明 |
|------|------|
| `apiKey` | football-data.org API Key；为空时跳过同步 |
| `competitionCode` | 赛事编码，世界杯使用 `WC` |
| `season` | 赛季年份，例如 `2026` |
| `cronSpec` | 轮询频率；当前 cron 使用 5 字段格式：分 时 日 月 周；为空默认 `*/30 * * * *` |

建议频率：

- 世界杯开赛前：每 6 小时一次。
- 小组赛/淘汰赛期间：每 30 分钟一次。
- 比赛日临近开赛窗口：可临时提升到每 5-10 分钟一次。

### 3.2 完整启动配置示例

以下片段只展示世界杯同步相关配置，需放入服务实际启动读取的 `bbs-go.yaml`：

```yaml
footballData:
  apiKey: "YOUR_FOOTBALL_DATA_API_KEY"
  baseURL: ""                  # 可选；留空使用 football-data 客户端默认地址
  competitionCode: "WC"        # World Cup
  season: 2026
  cronSpec: "0 */6 * * *"      # 5字段 cron：分 时 日 月 周；示例为每 6 小时
```

配置方法：

1. 复制示例配置：`cp bbs-go.example.yaml bbs-go.yaml`。
2. 将 `footballData.apiKey` 改为 football-data.org API Key；为空时 `SyncWorldCupSchedules` 会直接跳过，避免生产环境持续报错。
3. 世界杯使用 `competitionCode: "WC"`，`season` 填赛事年份。
4. 按运营阶段调整 `cronSpec`。例如 `*/30 * * * *` 表示每 30 分钟，`*/10 * * * *` 表示每 10 分钟。
5. 修改 `bbs-go.yaml` 后重启服务，定时任务会在进程启动时读取配置并注册。

注意：

- 当前调度器按 5 字段 cron 表达式注册，不要写成带秒字段的 6 字段表达式。
- `BBSGO_ENV=prod` 只决定运行环境；世界杯同步是否执行取决于 `footballData.apiKey`、`competitionCode`、`season` 和定时任务配置。
- 管理端手动触发同步时可临时覆盖 `competition/season`，但后台定时任务仍以 `bbs-go.yaml` 为准。

## 4. 数据流

```text
cron
  -> FootballSyncService.SyncWorldCupSchedules
    -> football-data /competitions/{code}/matches
      -> upsert MatchSchedule
        -> upsert PredictMarket
          -> upsert PredictContext
            -> PredictTagService 定时物化标签
```

### 4.1 MatchSchedule

外部赛程落库字段：

| 字段 | 来源 |
|------|------|
| `source` | 固定 `football-data` |
| `externalId` | football-data match id |
| `competition` | `m.Competition.Code`，兜底配置 `competitionCode` |
| `season` | 配置 `season`，兜底 `m.Season.Year` |
| `matchday` | football-data matchday |
| `stage` | football-data stage |
| `groupName` | football-data group |
| `status` | football-data status；当前只保存状态文本，不保存比分 |
| `utcDate` | 比赛 UTC 时间 |
| `homeTeam/awayTeam` | 主客队名称 |
| `homeTeamId/awayTeamId` | 主客队外部 ID |
| `homeScore/awayScore` | 建议新增：全场比分；仅 `FINISHED` 或有比分时写入 |
| `winner` | 建议新增：`A/B/DRAW/UNKNOWN`，由比分和市场类型映射得出 |
| `lastSyncedAt` | 本次同步时间 |

幂等键：

```text
source = football-data
external_id = football-data match id
```

### 4.1.1 主客队冻结规则

主客队身份是下注语义的一部分：

```text
A = homeTeam 胜
B = awayTeam 胜
```

因此一旦比赛场次已经确定主客队，后续同步不再覆盖主客队身份字段：

```text
homeTeam
awayTeam
homeTeamId
awayTeamId
```

建议判断规则：

```text
existing.homeTeamId > 0
existing.awayTeamId > 0
existing.homeTeam != ""
existing.awayTeam != ""
```

满足以上条件时：

- 保留站内已有主客队。
- 继续允许更新状态、开赛时间、比分、最近同步时间。
- 不用 football-data 后续返回的队名覆盖站内字段。

原因：

- 淘汰赛早期可能是 `Winner Group A`、`Runner-up Group B`、`TBD` 等占位。
- 外部源后续可能修正队名或语言，但下注市场的 A/B 已经绑定到站内展示。
- 若覆盖主客队，用户历史下注的 `A/B` 语义会变化。

如果确实需要纠错，应走运营接口，并记录操作日志。

### 4.2 PredictMarket

每个 `MatchSchedule` 对应一个站内预测市场。

幂等键：

```text
source_model = MatchSchedule
source_model_id = MatchSchedule.Id
```

生成规则：

| 字段 | 规则 |
|------|------|
| `title` | `{homeTeam} vs {awayTeam}`；缺队名时用 `TBD` |
| `marketType` | 小组赛 `1x2`，淘汰赛 `binary` |
| `status` | 双方球队都确定时 `OPEN`，否则关闭 |
| `closeTime` | `utcDate - 10分钟` |
| `result` | 小组赛可写 `A/B/DRAW`；淘汰赛只写 `A/B` |
| `sourceModel` | `MatchSchedule` |
| `sourceModelId` | 对应 `MatchSchedule.Id` |

注意：当前代码中关闭状态使用了 `CLOSE`，而预测市场主文档状态口径是 `CLOSED`。建议后续统一为 `CLOSED`，并兼容历史值。

### 4.2.1 小组赛/淘汰赛市场类型

同步赛程时必须先判断比赛阶段，再决定市场类型和下注选项。

小组赛：

```text
marketType = 1x2
A = 主队胜
B = 客队胜
DRAW = 平局
```

淘汰赛：

```text
marketType = binary
A = 主队胜
B = 客队胜
```

判断建议：

```text
小组赛：stage == GROUP_STAGE 或 groupName 非空
淘汰赛：stage in LAST_16 / QUARTER_FINALS / SEMI_FINALS / THIRD_PLACE / FINAL
```

如果 football-data 的 stage 命名有差异，应在同步服务中做兼容映射。无法识别阶段时，建议保守关闭市场并记录 warning，交运营确认后开放。

### 4.3 PredictContext

用于前端展示和标签聚合。

生成规则：

| 字段 | 规则 |
|------|------|
| `marketId` | `PredictMarket.Id` |
| `eventName` | 同 `PredictMarket.Title` |
| `proText` | `{homeTeam} 胜` |
| `conText` | `{awayTeam} 胜` |
| `drawText` | 建议新增：小组赛使用 `平局` |
| `tags` | `football,{competitionCodeLower}` |
| `listImage` | 列表展示图片；创建时为空，同步更新时不覆盖 |
| `sideABgImage/sideBBgImage` | A/B 阵营背景图；创建时为空，同步更新时不覆盖 |
| `sideABgColor/sideBBgColor` | A/B 阵营背景色；默认 `#E23D3D` / `#276EF1`，同步更新时不覆盖 |
| `imageUrl/detail` | 创建时为空；同步更新时不覆盖 |
| `heat/participantCount` | 创建时默认 0；同步更新时不覆盖 |

更新策略：

- 每次同步仅刷新系统派生字段：`eventName/proText/conText/tags`。
- 不覆盖运营手工维护字段：`imageUrl/detail/heat/participantCount`。
- 上下文说明、封面图、热度、参与人数只能通过运营接口修改。
- `tags` 是标签物化任务的数据源。

### 4.3.1 运营字段保护

同步流程禁止覆盖以下字段：

| 字段 | 说明 |
|------|------|
| `PredictContext.detail` | 上下文说明、运营文案 |
| `PredictContext.imageUrl` | 封面图 |
| `PredictContext.listImage` | 列表展示图片 |
| `PredictContext.sideABgImage/sideBBgImage` | A/B 阵营背景图 |
| `PredictContext.sideABgColor/sideBBgColor` | A/B 阵营背景色 |
| `PredictContext.heat` | 人工热度、榜单权重 |
| `PredictContext.participantCount` | 展示参与人数或运营校正值 |

这些字段只能由运营接口修改，例如：

```text
POST /api/football/predict_context/update
```

后续建议迁移到管理员接口：

```text
POST /api/admin/predict/context_update
```

这样可以避免每轮 football-data 同步把运营配置冲掉。
