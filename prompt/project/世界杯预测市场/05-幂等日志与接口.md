## 6. 幂等与并发

### 6.1 幂等约束

必须保证以下数据不会重复：

1. 同一 football-data match 只生成一条 `MatchSchedule`。
2. 同一 `MatchSchedule` 只生成一条 `PredictMarket`。
3. 同一 `PredictMarket` 只生成一条 `PredictContext`。

建议数据库唯一索引：

```text
MatchSchedule(source, external_id)
PredictMarket(source_model, source_model_id)
PredictContext(market_id)
```

### 6.2 重入控制

当前 scheduler 使用：

```go
cron.SkipIfStillRunning(cron.DefaultLogger)
```

同一个进程内，上一轮同步未结束时会跳过下一轮，避免任务重叠。

如果未来多实例部署，需要增加跨实例锁：

- 数据库 advisory lock。
- `t_job_lock` 表。
- Redis 分布式锁。

## 7. 错误处理与日志

### 7.1 失败处理

同步失败不应影响主服务运行：

- API Key 为空：记录 warning 后跳过。
- football-data 请求失败：记录 error，本轮退出。
- 单场落库失败：当前实现直接返回错误并终止本轮。

建议后续优化：

- 单场失败不影响后续比赛，记录失败列表。
- 增加 `sync_status` 或 `job_log`，便于后台查看最近同步结果。
- 对 429/rate limit 做退避。

### 7.2 关键日志

应至少保留：

```text
football-data api response received matches=...
football schedules synced matches=...
football schedule sync failed err=...
```

排查命令：

```bash
sudo journalctl -u bbs-go --no-pager -n 300 | grep -i "football"
```

FootballSyncService.SyncWorldCupSchedules

默认配置为空时使用：

*/30 * * * *

## 9. 与预测市场下注/结算的关系

通用下注、运营结算、用户结算业务流已抽取到：[预测市场公共部分](../预测市场公共部分/00-目录.md)。本节只保留世界杯同步和赛果来源如何接入公共结算的说明。

世界杯同步只负责创建和更新来源市场，不单独实现下注、扣金币、派奖。

公共链路分工：

- 用户下注：复用公共 `POST /api/coin/bet`。
- 运营结算：复用公共 `POST /api/admin/predict/market/settle`。
- 用户领取结算：复用公共 `POST /api/coin/settle`。

世界杯来源只负责把 `MatchSchedule` 和比分结果映射到 `PredictMarket.marketType/result/status`。

注意：用户结算服务不读 `MatchSchedule.status`，也不读 football-data 结果。它只读：

```text
PredictMarket.status == SETTLED
PredictMarket.result == A or B or DRAW
```

比赛结果驱动结算的来源侧链路：

```text
football-data FINISHED
  -> 保存 MatchSchedule 比分
    -> 小组赛：按 A/B/DRAW 映射结果
      -> 写 PredictMarket.result = A/B/DRAW
      -> 写 PredictMarket.status = SETTLED 或进入运营确认
    -> 淘汰赛非平局：按 A/B 映射胜方
      -> 写 PredictMarket.result = A/B
      -> 写 PredictMarket.status = SETTLED 或进入运营确认
    -> 淘汰赛平局：记录错误日志
      -> PredictMarket.status = CLOSED
      -> 运营人员手动结算/作废/退款
```

当前需要明确的问题：

- 比赛取消/延期时是否退款。
